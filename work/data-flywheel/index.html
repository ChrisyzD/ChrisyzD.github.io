LLM data flywheel

Training data for a multi-model in-vehicle voice assistant. Instead of generating more data everywhere, measure first — then regenerate only where the failures are.

June – August 2026 · Undergraduate thesis, UM–SJTU Joint Institute · Python, LLM agents, retrieval

My scope. I owned the data pillar: the user simulator, the rollout and judging harness, the deterministic governance layer, and the targeted regeneration. The figures below are end-to-end system numbers; the pillar I owned is one input into them. Done part-time, alongside the Lark internship over the same summer.

What & why

When an assistant is weak, the reflex is to generate more training data. That scales cost linearly and quality barely at all, because most of the new data lands where the model was already fine.

The alternative is to build the ruler first and let it aim the spending. Simulate users, roll the assistant out against them, score the rollouts, and then read the error breakdown rather than the score — because the breakdown is what tells you which functions to regenerate against. The score is a summary; the breakdown is a work order.

What I built

  • A user simulator with 41 persona archetypes and explicit state control, so a conversation has a goal and a memory rather than drifting.
  • Retrieval-grounded rollouts: candidate tools retrieved at top-K = 20 and grounded into the conversation, so the assistant is answering against a real tool surface instead of an imagined one.
  • An LLM-judge harness running on a GPU cluster, plus a deterministic governance layer — hard rules that pass or fail without a model's opinion — in front of it.
  • A four-quadrant corpus: positive and negative examples crossed with single-turn and multi-turn, so the fine-tune sees refusals and recoveries, not only successes.
  • Targeted regeneration against the 11 highest-error functions the judge's breakdown exposed, rather than uniform generation.

Results & boundary

  • 17,200 verified (reward = 1) fine-tuning dialogues came out of the pipeline.
  • Fine-tuning on that corpus raised judge-adjusted answer acceptance 72.8% → 82.7%.
  • The strict multi-turn all-correct rate went 39.9% → 60.0%.
  • No-tool false positives — the assistant answering when it should have called a tool — fell 4,424 → 1,410.
  • Boundary: this is an undergraduate thesis, not production. Every figure above is scored by an LLM judge, which is exactly the thing I am least comfortable with; see below.

Further thoughts

Where the system's numbers stop and my part of them starts — and the two checks I would run first if I picked this up again.

Start with the boundary, because it is the thing I get wrong most easily when I talk about this project. “I owned the data pillar” is a convenient phrase and it hides a seam. The four numbers above belong to the whole system; the pillar is one input into them. When I describe this work I try to keep that order — here is what the system did, here is the part of it that was mine — rather than letting the two blur together, because the blurring is effortless and one-directional and always flatters me.

The first check I owe it is about the judge. reward = 1 is the judge's verdict, the corpus was filtered on that verdict, and the improvement afterwards was scored by a judge rather than by a person — so the judge is grading work the judge helped produce. Some fraction of 72.8 → 82.7 is the assistant getting better; some fraction may be the assistant learning what a judge likes; I cannot give you the split.

What would settle it is a held-out slice scored by hand, or scored by a judge from a different model family. I cannot point you at one, and a check I cannot point at is not a check I should lean on. Until it exists the number is a strong internal signal and a weak external claim, and I would rather say that than let it be read as the second thing.

The second check is a denominator. 17,200 is a numerator I can quote; the generated-and-discarded count that belongs beside it is not something I can put on this page. That yield is the interesting quantity — it is what separates a simulator that produces usable conversations from a governance layer doing all the filtering downstream of a noisy one. It is why this figure stays a count of what exists rather than a rate of anything, and it is the first number I would put on the wall next time.
