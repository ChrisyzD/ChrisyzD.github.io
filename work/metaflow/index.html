MetaFlow

A metadata-centric natural-language-to-SQL system: questions are resolved through an inspectable relational intermediate representation instead of generating SQL directly, so an answer arrives with its source, its definition and its verification attached.

March 2026 – present · Python, FastAPI, PostgreSQL, React, TypeScript

Who did what

MetaFlow is a two-person project. Putting the boundary second on this page rather than in a footnote is deliberate — you should not have to hunt for it.

  • I own the metadata layer, the gold-case regression suite, the contracts endpoint, and the React/TypeScript studio front end.
  • My collaborator owns the NL→IR→SQL engine core.

I am not naming my collaborator here without their say-so.

The idea

A question first lands in a relational intermediate representation — a structured object that states what the system intends to compute — and SQL is compiled from that. The reason is not elegance. It is that an IR is something a person can read before anything runs, and something a machine can check.

When SQL is generated directly, a wrong answer is a debugging problem: you read the query top to bottom and guess which clause betrayed you. When there is an IR, a wrong answer has an address — this field bound to the wrong measure, that filter dropped. Wrongness stops being a mood and becomes a location.

How I check it

Before we built features, we pinned 20 gold-case scenarios. Each is pinned across all five pipeline stages, with the expected output at every stage, kept in version control. When a schema moves or a definition changes, I do not have to ask whether something broke — I re-run the suite and it names the stage and the case.

Data quality works the same way. Contracts are written as executable expectations, and the FastAPI backend exposes a contracts endpoint that enforces them, so a rule I wrote down is a rule that runs. Contract as test.
