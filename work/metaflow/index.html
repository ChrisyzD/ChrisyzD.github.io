MetaFlow

A metadata-centric natural-language-to-SQL system: a question is resolved through an inspectable relational intermediate representation instead of generating SQL directly, so an answer arrives with its source, its definition and its verification attached.

March 2026 – present · Python, FastAPI, PostgreSQL, React, TypeScript

My scope. Two-person project. I own the metadata layer, the gold-case regression suite, the contracts endpoint and the React/TypeScript studio front end; my collaborator owns the NL→IR→SQL engine core. I am not naming them here without their say-so.

Why an IR instead of SQL

Most natural-language-to-SQL systems generate a query and run it. When the number that comes back is wrong, nothing tells you where it went wrong: you read the SQL top to bottom and guess which clause betrayed you.

So a question here lands first in a relational intermediate representation — a structured object stating what the system intends to compute — and SQL is compiled from that. The reason is not elegance. It is that an IR is something a person can read before anything runs, and something a machine can check. A wrong answer stops being a mood and becomes an address: this field bound to the wrong measure, that filter dropped.

What I built

The suite, before the features. We pinned 20 gold-case scenarios before building. Each is pinned across all five pipeline stages, with the expected output at every stage, kept in version control. When a schema moves or a definition changes, I do not have to ask whether something broke — I re-run the suite and it names the stage and the case.

Contracts that run. Data-quality rules are written as executable expectations, and the FastAPI backend exposes a contracts endpoint that enforces them, so a rule I wrote down is a rule that runs. Contract as test.

The studio. Interface, annotations and data are all English. The data is the jaffle_shop demo dataset: synthetic rows generated against dbt's public jaffle_shop schema — 50,000 orders spanning 2022 to 2025 — not the toy seed data that ships with dbt. The system is organized around four ideas: answers are bounded by a certified capability list, every answer carries provenance, anything out of scope is refused explicitly rather than guessed, and the fix behind a refusal goes through lineage analysis, a dry run and an explicit owner approval before it ships.

The first and the last of those ideas are the two frames at the top of this page: the explicit refusal, and the provenance card that ships with the answer once the gap behind the refusal has been closed.

Further thoughts

The gold-case suite was written by the same person who built the metadata layer it is meant to police — me. That is convenient, and it means the twenty scenarios encode my blind spots along with my intent. They catch regressions against what I already thought to check; they say nothing about the case I never imagined. So the suite grows only when something fails in a way somebody noticed, which is an argument for putting it in front of people who did not build it.

The lineage goes to the table, not the column. What the impact analysis flags is a whole downstream capability, which is the coarse version of lineage and the version that is tractable in a two-person project. Lineage that tells you which column is affected is a much harder thing to build than the diagram admits. I would rather write that down here than be asked it in a room.

The prototype is probably more convincing than the system behind it, and that is the trap. A good mock is always more complete than the thing it stands in for, it costs a fraction as much, and on a personal site nobody is checking which one they are looking at.
