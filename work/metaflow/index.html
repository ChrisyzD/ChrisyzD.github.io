MetaFlow

A metadata-centric natural-language-to-SQL system: a question is resolved through an inspectable relational intermediate representation instead of generating SQL directly, so an answer arrives with its source, its definition and its verification attached.

March 2026 – present · Python, FastAPI, PostgreSQL, React, TypeScript

My scope. Two-person project. I own the metadata layer, the gold-case regression suite, the contracts endpoint and the React/TypeScript studio front end; my collaborator owns the NL→IR→SQL engine core. I am not naming them here without their say-so.

What & why

Most natural-language-to-SQL systems generate a query and run it. When the number that comes back is wrong, nothing tells you where it went wrong: you read the SQL top to bottom and guess which clause betrayed you.

So a question here lands first in a relational intermediate representation — a structured object stating what the system intends to compute — and SQL is compiled from that. The reason is not elegance. It is that an IR is something a person can read before anything runs, and something a machine can check. A wrong answer stops being a mood and becomes an address: this field bound to the wrong measure, that filter dropped.

What I built

The ruler, before the features. We pinned 20 gold-case scenarios before building. Each is pinned across all five pipeline stages, with the expected output at every stage, kept in version control. When a schema moves or a definition changes, I do not have to ask whether something broke — I re-run the suite and it names the stage and the case.

Contracts that run. Data-quality rules are written as executable expectations, and the FastAPI backend exposes a contracts endpoint that enforces them, so a rule I wrote down is a rule that runs. Contract as test.

The studio. The screens below are from the design prototype for the front end, annotated in English. Design prototype — not the running system. They show the four ideas the system is organised around: answers are bounded by a certified capability list, every answer carries provenance, anything out of scope is refused explicitly rather than guessed, and the fix behind a refusal goes through lineage analysis, a dry run and an explicit owner approval before it ships.

  1. Impact analysis automatically flags one downstream capability (semantic_tier_migration) that needs recertification before the patch can ship.
  2. A transactional dry-run (BEGIN … ROLLBACK) proves the exact row count and a checksum that still matches on a second, independent recomputation — before anything real is written.
  3. Any write to a certified layer needs an explicit owner sign-off, and the approval card carries the dry-run and validation evidence that justified it.
  4. Approval is not the end of the flow: it triggers the write, registers the new capability, and notifies the business user whose question started the ticket.

Further thoughts

Working notes — first person, unfinished, and mine to revise. They are here because the argument for a system like this is only as good as its author's willingness to say where it is thin.

The number missing from this page is the engine's pass rate. It would be the most persuasive line here and I am not going to write it, because I have not run that evaluation end to end. The suite I built reports which stage broke on which case; it does not currently produce a headline score I would defend under questioning. I would rather this page be short a number than carry one I reverse-engineered from a feeling.

The gold cases were written by the same person who built the metadata layer. That is convenient, and it means the suite encodes my blind spots along with my intent. Twenty scenarios pinned across five stages catch regressions against what I already thought to check; they say nothing about the case I never imagined. So the honest description of the ruler is that it grows only when something fails in a way somebody noticed — which is an argument for getting it in front of people who did not build it, not an argument for pinning more cases myself.

I keep the prototype label on those screens for a reason: a good mock is more complete than the system behind it, and on a personal site nobody is checking. The same caution applies to the impact analysis. What it flags is a whole downstream capability — that is the coarse, table-level version of lineage, and it is the version that is tractable. Lineage that tells you which column is affected is a much harder thing to build than the diagram admits, and I would rather say that here than be asked it in a room.
