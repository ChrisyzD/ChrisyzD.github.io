LLM Data Flywheel for In-Vehicle Voice Assistants

Jun – Aug 2026 · Undergraduate thesis, UM–SJTU Joint Institute · Python

I owned the data pillar of a multi-model in-vehicle voice assistant: instead of generating more training data everywhere, measure first, then regenerate only where the failures are.

  • Built a user simulator (41 persona archetypes, explicit state control) with retrieval-grounded rollouts, LLM-judge scoring and a deterministic governance layer, yielding 17,200 verified (reward = 1) fine-tuning dialogues, with targeted error-regeneration on the 11 highest-error functions.

Cardiac Rehabilitation Wearable Study

Apr 2025 – Jan 2026 · Research assistant (SURE summer program, then continued on the study) · University of Michigan

Cardiac rehab is prescribed as a fixed 36-session protocol for everyone. The question was whether wearable data can say when a given patient has actually stopped improving.

  • Assembled the analysis dataset: reconciled 400K+ raw step records from multiple sources onto one per-patient daily timeline, and set missing-value and cleaning rules that cut 247 enrolled patients to a 191-patient analysis cohort.
  • Engineered temporal features (rolling averages, trend slope, periodicity) feeding K-means/PCA phenotyping and plateau detection against the standard 36-session model; ~68% of that cohort had suboptimal discharge timing.
Cleaning
DateTime standardization · type unification · missing-value marking · exercise-time capping (> 300 min) · step-count anomaly detection
Features
2-week / 4-week moving averages · week-over-week change rate · trend slope · coefficient of variation · stable-week count
Plateau detection
v1: change rate < 20%, CV < 0.30, duration ≥ 3 weeks → v2: minimum wait 8 weeks, moving-average slope < 200, change rate < 25%, multi-metric. Later extended with a Kalman-filter approach.
Phenotyping
K-means (k = 2): higher-baseline / stable-progression / later-plateau vs lower-baseline / slower-progress / earlier-plateau

So what: the hard part was not the model, it was deciding what “recovered” means and then showing how much that decision moves the answer.

Most natural-language-to-SQL demos give you a number and no way to tell whether it is right. This is what I changed in my own projects to make that different, and what it cost.

  • An intermediate representation you can read before anything runs turns “the answer is wrong” into “this field is wrong”.
  • Build the ruler before the feature: twenty gold cases pinned across five stages, and contracts written as tests that actually run.
  • The step people skip is turning each fix into a guardrail, so the ruler grows on its own and the same mistake cannot happen twice.
