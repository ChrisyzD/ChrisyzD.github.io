The loop

Notes on making an NL-to-SQL answer checkable.

Chris Dai · August 2026 · ~9 min · All figures come from the jaffle_shop demo dataset.

Most natural-language-to-SQL demos work the same way. You ask a question, a model writes SQL, the SQL runs, a number comes back. When the number is wrong, nothing tells you. When it is right, you don't know why.

I have been building MetaFlow since March 2026 at Shenzhen Legion Technology, with one collaborator. It is a two-person project: I own the metadata layer, the evaluation suite and the studio front end; my collaborator owns the query engine. The first design decision we made was not to generate SQL.

1. It starts with not trusting the answer

A question first lands in a relational intermediate representation. The IR spells out what the system intends to compute, as a structured object rather than prose or SQL. You can read it before anything executes, and so can a machine.

That one move changes what “wrong” means. A wrong SQL string is a debugging problem: you read it top to bottom and try to guess which clause betrayed you. A wrong IR has an address. It bound revenue to the wrong measure. It dropped the time filter. It resolved gold customers against the wrong table. You can point at the field.

Trust does not come from a model sounding confident. It comes from there being somewhere to look before you commit.

What “has an address” means

The IR is a small set of named slots, and each one is a place a mistake can live:

  • measure — which number is being summed
  • grain — what one row of the result is
  • filters — including the time window, the one most often silently dropped
  • entity binding — which table gold customer resolved against
  • decisions — the definition records this answer inherits

“The answer is wrong” becomes “the entity binding is wrong”, which is a sentence somebody can act on.

2. Build the ruler before the feature

Before we built features, we pinned twenty gold-case scenarios. Each one is pinned across all five pipeline stages, from the natural-language input through to the final design, with the expected output at every stage, in version control.

The point is not test coverage. The point is that the ruler exists before the thing it measures. When a schema moves or a definition changes, I don't have to ask whether something broke. I re-run the suite and it tells me which stage broke, on which case.

The same idea covers data quality. Contracts are written as executable expectations and the backend has an endpoint that enforces them, so a rule I wrote down is a rule that runs. Contract as test.

An untested change to metadata is not a small change. It is a silent change to every answer downstream of it.

What a gold case is

Not an assertion on the final number. One row per scenario, with the expected artifact at every stage of the pipeline:

  • the natural-language question, as a user would type it
  • the entities and metrics it should resolve to
  • the intermediate representation it should compile to
  • the SQL that IR should produce
  • the shape and value of the result

A failure names a cell, not a suite. That is the whole reason it is a grid rather than a list of assertions.

3. The one thing you cannot automate

Here is a real question from the demo dataset: what was net revenue from gold-tier customers in 2024?

It has two defensible answers. Gold at the time of the order, or gold as of today? Two source tables disagree, because they were built to answer different questions. No amount of modeling resolves this. Someone has to decide.

So the decision is treated as an asset instead of a conversation. It is recorded with an id, the chosen rule — tier at order time — and the reason. Every answer that depends on it points back to it. When someone disagrees six months later, they are arguing with a record, not with a memory.

This is the only step in the chain that cannot be automated, and it is why I say metadata is the source of truth rather than the database. The ceiling on answer quality is not the model. It is whether anyone wrote down what the words mean.

The decision, as a record

What “treated as an asset” means in practice — the fields the studio in the MetaFlow prototype actually stores:

  • id — OD001, so an answer can cite it
  • rule — tier as of the order date, not as of today
  • reason — the question is about 2024 behaviour, so the 2024 tier is the one that was in force
  • owner — a person, not a team
  • bound to — every metric version that inherits it

The point of the id is that the disagreement six months later has an address.

4. The loop

Measure, locate, fix, turn the fix into a guardrail, measure again.

The fourth step is the one that gets skipped. A fix that only fixes today's bug buys you one day. A fix that also becomes a new gold case buys you every day after that. The ruler grows with the failures, and the same mistake does not get to happen twice.

I ran the same loop in a different domain for my undergraduate capstone, on training data for an in-vehicle voice assistant. That was a five-person team system, and what I led end to end was the data flywheel for one of its three domains: I built the user simulator with 41 persona archetypes and explicit state control, produced retrieval-grounded conversation rollouts, and scored them with an LLM judge. A teammate owned the model-routing pillar. The figures below are end-to-end system numbers; the corpus I produced is one input into them.

The judge's value was not the score. It was the error breakdown: it showed which eleven functions had the highest error rates. Instead of generating more data everywhere, I regenerated data aimed at those eleven. Fine-tuning on the resulting 17,200 verified dialogues lifted the system's judge-adjusted answer acceptance from 72.8% to 82.7%, and its strict multi-turn all-correct rate from 39.9% to 60.0%.

Generating more data everywhere would have been easier to write and worse. Measuring first is what made the eleven functions visible at all.

Some fraction of 72.8 → 82.7 is the assistant getting better; some fraction may be the assistant learning what a judge likes. 5. One second on stage, a thousand lines backstage

Someone types a question into a chat box and gets $340,955.56 back in about a second: certified net revenue from gold-tier customers in 2024.

Not long before, that question had no answer. Six stations stand behind the one second:

  • Audit. 8,611 of 50,000 orders had no resolvable customer tier.
  • The definition decision. Tier at order time, recorded with an owner and a reason.
  • Repair. A temporal join closed the gap. The patch shipped as four things, not one: the patch, a dry run, a verification, and a rollback plan.
  • Semantic asset. The repaired result became a certified table you can query directly, registered in a capability list so the system knows what it is allowed to answer.
  • Contract. Intent, the bound decision, the expected value, a fingerprint of the result — and counter-examples showing the wrong ways to compute it.
  • Daily re-verification. An automated check suite re-proves the number every day. When a check fails, the number comes down instead of quietly going wrong.

Together that is roughly a thousand lines of code and rules, and about five person-days.

Where these numbers come from

$340,955.56, 8,611 and 50,000 are all from the jaffle_shop demo dataset — synthetic rows generated against dbt's public jaffle_shop schema, spanning 2022 to 2025. The schema is public; the rows are not real, and the figure is not a claim about anybody's revenue.

Roughly a thousand lines and about five person-days are my own estimates for one metric on a two-person project, not a benchmark. I quote them because the shape of the ratio is the argument — the foundation is a one-time cost — and not because either number would survive being audited.

Two things follow. The foundation is a one-time cost and metrics are marginal after it — the second certified metric on the same base costs a fraction of the first. And every light moment on stage has a station underneath holding it up.

The deliverable of data engineering is not SQL. It is a number that gets re-proved every day.

What I take from this

Both of these systems are small. A two-person project and a capstone are not production infrastructure, and I am not going to pretend otherwise. What transfers is the habit: build the ruler before the feature, write down what the words mean, and make every fix into a guardrail so the ruler grows on its own.

If an answer cannot be checked, it is not an answer. It is a guess with formatting.
